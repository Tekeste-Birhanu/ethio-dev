# Data Schema

## 1. Overview

- **Database / storage:** Supabase PostgreSQL; Supabase Auth owns authentication identities; Supabase Storage owns attachment bytes.
- **Schema status:** T-01 foundation modules include the core entities, relationships, indexes, constraints, and data invariants drafted in `supabase/migrations/20261018000100_create_core_schema.sql`, RLS and trusted workflow policies drafted in `supabase/migrations/20261018000200_authorization_and_workflows.sql`, and Storage policies/cleanup drafted in `supabase/migrations/20261018000300_storage_policies_and_cleanup.sql`. Hosted bucket setup, clean-project migration application, and verification remain for T-03.
- **Source of truth:** PostgreSQL is canonical for application records, authorization relationships, chat history, and notification state. Auth is canonical for authentication identity and verified email state. Storage is canonical for attachment bytes.
- **Conventions:** Use `snake_case`; UUID primary keys generated by PostgreSQL; `timestamptz` timestamps stored in UTC; `created_at` and `updated_at` on mutable user-facing records; foreign keys and constraints enforce integrity. Public profile usernames are case-sensitive. Skills are normalized for case-insensitive matching.
- **Authorization:** React accesses Supabase directly. RLS protects every exposed table and Storage object; database functions enforce multi-row transitions. Browser-provided roles and metadata are never trusted.

## 2. Entities

The following is a logical schema. Migration SQL may use equivalent types or normalization if the invariants and access rules remain the same.

### `profiles`

- **Purpose:** Public developer profile linked one-to-one to a Supabase Auth user.
- **Fields:**

| Field                      | Type          | Required | Rules / notes                                                                              |
| -------------------------- | ------------- | -------: | ------------------------------------------------------------------------------------------ |
| `user_id`                  | `uuid`        |      Yes | Primary key and FK to `auth.users.id`. Self-service account deletion is outside MVP scope. |
| `username`                 | `text`        |      Yes | Unique, case-sensitive; validate allowed characters and length at the database boundary.   |
| `display_name`             | `text`        |      Yes | Public name; validate length and trim surrounding whitespace.                              |
| `bio`                      | `text`        |       No | Public; bounded length.                                                                    |
| `city_id`                  | `uuid`        |       No | FK to predefined `cities`; mutually exclusive with `city_other`.                           |
| `city_other`               | `text`        |       No | User-entered city when the `Other` option is selected; mutually exclusive with `city_id`.  |
| `avatar_path`              | `text`        |       No | Storage object reference; public exposure requires an intentional public avatar policy.    |
| `created_at`, `updated_at` | `timestamptz` |      Yes | Database-generated timestamps.                                                             |

Profile skills and external links use separate tables below. Email, provider tokens, and verification state are not duplicated into the public profile.

### `skills` and `profile_skills`

- **Purpose:** Maintain a growing shared skill catalog and connect skills to developer profiles and opportunities.
- **Fields (`skills`):**

| Field             | Type          | Required | Rules / notes                                                                                |
| ----------------- | ------------- | -------: | -------------------------------------------------------------------------------------------- |
| `id`              | `uuid`        |      Yes | Primary key.                                                                                 |
| `name`            | `text`        |      Yes | Display form of the skill.                                                                   |
| `normalized_name` | `text`        |      Yes | Case-folded, trimmed key with a unique constraint; `React` and `react` resolve to one skill. |
| `created_by`      | `uuid`        |       No | Auth user that first added it.                                                               |
| `created_at`      | `timestamptz` |      Yes | Database-generated timestamp.                                                                |

- **Fields (`profile_skills`):** `user_id uuid` FK to `profiles`; `skill_id uuid` FK to `skills`; composite primary key `(user_id, skill_id)`.
- **Rules:** A user-entered unknown skill is added to the shared catalog automatically through a normalized, race-safe database operation. Catalog entries remain in the shared catalog.

### `cities`

- **Purpose:** Provide consistent location choices and searchable city filters.
- **Fields:** `id uuid` primary key; `name text` display name; `normalized_name text` unique normalized key; `country_code text` default `ET`; `is_active boolean` default true; `sort_order integer`.
- **Rules:** Seed these predefined Ethiopian cities in the agreed order: Addis Ababa, Adama, Bahir Dar, Dire Dawa, Hawassa, Jimma, Mekelle, Gondar, Dessie, Bishoftu, Shashamane, Harar, Arba Minch, Wolaita Sodo, and Jijiga. The UI also offers `Other`, whose text value is stored on the profile or opportunity rather than added to the shared city catalog. Deactivate rather than delete a city already in use.

### `profile_links`

- **Purpose:** Store optional external links on public profiles.
- **Fields:** `id uuid`; `user_id uuid` FK to `profiles`; `label text`; `url text`; `sort_order integer`; timestamps.
- **Rules:** Validate URL scheme and length; allow only the product's approved web URL schemes. Profile owner manages their links.

### `opportunities`

- **Purpose:** Public project listings that recruit collaborators and may later be retained privately with accepted collaboration history.
- **Fields:**

| Field                      | Type          |    Required | Rules / notes                                                                                                                      |
| -------------------------- | ------------- | ----------: | ---------------------------------------------------------------------------------------------------------------------------------- |
| `id`                       | `uuid`        |         Yes | Primary key.                                                                                                                       |
| `creator_id`               | `uuid`        |         Yes | FK to `profiles`; creator manages the listing while it is public.                                                                  |
| `title`                    | `text`        |         Yes | Bounded length.                                                                                                                    |
| `description`              | `text`        |         Yes | Project idea and collaboration context.                                                                                            |
| `project_type`             | `text`        |         Yes | One of `web`, `mobile`, `desktop`, `game`, `developer_tool`, `data_ai`, `hardware_iot`, `other`.                                   |
| `project_type_other`       | `text`        | Conditional | Required only when `project_type = other`; otherwise null.                                                                         |
| `experience_levels`        | `text[]`      |         Yes | One or more of `beginner_friendly`, `junior`, `intermediate`, `experienced_mentor`, `any_level`; selection is multi-valued.        |
| `commitment`               | `text`        |          No | Legacy compatibility field. The current product does not collect, display, or filter by this value; existing data remains stored.  |
| `city_id`                  | `uuid`        |          No | FK to `cities`; mutually exclusive with `city_other`.                                                                              |
| `city_other`               | `text`        |          No | Text for the `Other` location option.                                                                                              |
| `status`                   | `text`        |         Yes | Listing state: `open` or `closed`; default `open`. Deletion changes visibility/state while preserving accepted collaboration data. |
| `deleted_at`               | `timestamptz` |          No | Soft deletion marker used to remove public listing and retain private project context when accepted collaborators/workspace exist. |
| `created_at`, `updated_at` | `timestamptz` |         Yes | Database-generated timestamps.                                                                                                     |

- **Constraints:** `project_type_other` is present iff type is `other`; `city_id` and `city_other` are mutually exclusive; experience list is nonempty and contains no duplicates. `any_level` is exclusive and cannot appear with specific experience levels. Opportunity listing state (`open` / `closed`) is separate from project state (`active` / `paused` / `completed`).
- **Deletion behavior:** If accepted collaboration or a workspace exists, soft-delete the opportunity (`deleted_at`), revoke public access, delete likes/comments and all non-accepted requests, and retain the opportunity details plus accepted collaboration/chat/workspace context for authorized participants. If no accepted collaboration or workspace exists, hard-delete the opportunity and its dependent records. In both cases, remove the listing from public discovery.
- **Related requirements:** F-03, F-04, F-06, F-08.

### `opportunity_skills`

- **Purpose:** Associate opportunities with skills from the shared catalog.
- **Fields:** `opportunity_id uuid` FK to `opportunities`; `skill_id uuid` FK to `skills`; composite primary key.
- **Rules:** Opportunity creator manages associations. Skills are searchable through the shared catalog.

### `opportunity_likes`

- **Purpose:** Record a user's current like on an opportunity.
- **Fields:** `opportunity_id uuid`; `user_id uuid`; `created_at timestamptz`; composite primary key `(opportunity_id, user_id)`.
- **Rules:** Any authenticated user may like/unlike an undeleted open or closed listing; email verification is not required. Each user can read their own like row. Public views expose only an aggregate count, not liker identities. Deleting an opportunity removes its likes.

### `comments`

- **Purpose:** Store opportunity comments and replies at arbitrary nesting depth.
- **Fields:** `id uuid`; `opportunity_id uuid`; `author_id uuid`; `parent_comment_id uuid` nullable self-FK; `body text` nullable; `created_at`, `updated_at`; `edited_at` nullable; `deleted_at` nullable.
- **Rules:** Parent comment must belong to the same opportunity. Author edits/deletes own comments; opportunity owner may delete any comment. Deleting a comment clears its body and sets `deleted_at`, preserving its ID and parent link so replies and thread position remain. Public thread reads render a generic deleted-comment placeholder without the deleted body or author. The UI displays a root comment followed by one flat list of all descendant replies, with each reply identifying its direct parent by username; the stored parent link remains unchanged. Closed listings accept comments. Deleting an opportunity removes all its comments and replies.

### `collaboration_requests`

- **Purpose:** Track a developer's requests to join an opportunity and the creator's decision.
- **Fields:** `id uuid`; `opportunity_id uuid`; `applicant_id uuid`; `message text` nullable; `status text`; `created_at`, `updated_at`; `decided_at timestamptz` nullable.
- **Allowed status:** `pending`, `accepted`, `rejected`, `withdrawn`.
- **Rules:** Only verified users may submit to an open opportunity. A unique constraint on `(opportunity_id, applicant_id)` permits one request row at a time. Rejected and withdrawn rows remain terminal and prevent resubmission. Closing an opportunity deletes pending request rows silently; if the opportunity reopens, affected applicants may create a fresh request. Deleting an opportunity removes all non-accepted requests. Acceptance path is selected atomically by the creator and recorded as `private_chat` or `workspace` (`acceptance_path text`, null until accepted and required on accepted requests). Accepted records remain if the opportunity is later deleted.

### `private_conversations`, `private_messages`, and `private_attachments`

- **Purpose:** One-to-one pre-workspace collaboration chat created when a request is accepted through the private-chat path.
- **Conversation fields:** `id uuid`; `request_id uuid` unique FK to an accepted request whose path is `private_chat`; `participant_a uuid` (opportunity creator); `participant_b uuid` (applicant); `status text` (`active` / `ended`); `created_at`; `ended_at` nullable. The participants must be distinct.
- **Message fields:** `id uuid`; `conversation_id uuid`; `sender_id uuid`; `body text`; `message_type text` (`user` / `system`, default `user`); nullable `workspace_id uuid` for workspace transition notices; `created_at timestamptz`; optional client idempotency key unique per conversation/sender.
- **Attachment fields:** `id uuid`; `message_id uuid`; `storage_path text` unique; `original_name text`; `media_type text`; `size_bytes bigint`; `uploaded_by uuid`; `created_at timestamptz`.
- **Rules:** Exactly the two request participants may access an active conversation. Ending it removes access and deletes messages and attachment objects; keep only the minimum tombstone/request state needed to prevent reapplication. Trusted workspace transitions may add a system message with a link to the resulting workspace. Clients can send user messages but cannot create system messages. Files are in private Storage and must pass the approved allowlist and 10 MB limit. Treat files as downloads unless they are safely previewable.

### Attachment allowlist

Use this allowlist for chat attachments, validating both extension and declared media type at upload. The per-file application limit is 10 MB. Do not allow archives, executables, audio, or video.

| Category       | Extensions                       | MIME types                                                                |
| -------------- | -------------------------------- | ------------------------------------------------------------------------- |
| Images         | `.jpg`, `.jpeg`, `.png`, `.webp` | `image/jpeg`, `image/png`, `image/webp`                                   |
| PDF and text   | `.pdf`, `.txt`, `.csv`           | `application/pdf`, `text/plain`, `text/csv`                               |
| Microsoft Word | `.docx`                          | `application/vnd.openxmlformats-officedocument.wordprocessingml.document` |

### Project records: `workspaces` and `workspace_memberships`

- **Product terminology:** Users see a Collabspace as one shared space containing members, chat, files, tasks, milestones, and settings. Database table/column/function names retain `workspaces` and `workspace_*` identifiers for implementation compatibility; `/projects` is also a legacy route. There is no separate user-facing Workspace or Project navigation concept.

- **Purpose:** Provide one shared Collabspace per opportunity with membership and role-based access.
- **Project fields:** `id uuid`; `opportunity_id uuid` unique FK; `owner_id uuid`; `created_by uuid`; `project_status text` (`active`, `paused`, `completed`); timestamps. `owner_id` and `created_by` are the opportunity creator for the MVP; ownership transfer is out of scope.
- **Membership fields:** `id uuid`; `workspace_id uuid`; `user_id uuid`; `role text` (`owner`, `admin`, `member`); `joined_at timestamptz`; `ended_at timestamptz` nullable; `ended_reason text` nullable; `invited_by uuid` nullable.
- **Invitation records:** No separate pending-invitation table is needed. An invitation takes effect immediately by creating an active membership; `invited_by` records who invited the member. Create the corresponding in-app notification in the same trusted operation.
- **Rules:** Enforce one project per opportunity and one active membership per project/user. A creator may create a project manually only after at least one accepted request, or atomically while accepting a request into the project path. The creator is the permanent owner and must remain an active member; the owner cannot leave or be removed while ownership transfer is out of scope. The creator appoints admins. Owner/admins invite and remove other members; non-owner members may leave. The owner alone may pause, complete, or delete the project. Paused projects may return to Active. Completed projects are final. Deleting a project removes memberships, chat history and attachment metadata, tasks, milestones, showcase, and project/task notifications, while queuing private Storage object deletion through the Storage API. The opportunity and accepted collaboration history remain. A project can remain after opportunity deletion. Access checks use current active membership; removal/departure revokes access to all project messages and files, including historical content, while the records remain available to current members.

### `workspace_messages` and `workspace_attachments`

- **Purpose:** Persist project chat messages and metadata for project file attachments.
- **Fields:** Same shape as private messages/attachments with `workspace_id` replacing `conversation_id`; use separate tables or a rigorously constrained common model.
- **Rules:** Only current active project members can read history or write. Realtime access and Storage RLS derive from active membership, not client-provided channel/path values. Removing a member immediately revokes access to all historical and new content. Project chat records and objects are retained for remaining members when a member leaves or is removed.

### `milestones`, `tasks`, and `task_assignees`

- **Purpose:** Organize project work and progress.
- **Milestone fields:** `id uuid`; `workspace_id uuid`; `title text`; `description text` nullable; `completion_mode text` (`automatic` / `manual`, default `automatic`); `is_completed boolean` default false; `created_by uuid`; timestamps.
- **Task fields:** `id uuid`; `workspace_id uuid`; `milestone_id uuid not null` composite FK to the same project's milestone; `title text`; `description text` nullable; `status text` (`to_do`, `in_progress`, `done`); `due_at timestamptz` nullable; `created_by uuid`; timestamps.
- **Assignee fields:** `task_id uuid`; `user_id uuid`; `assigned_by uuid`; `assigned_at timestamptz`; composite key `(task_id, user_id)`.
- **Rules:** Every task belongs to exactly one milestone. Projects must have a milestone before any tasks can be created. New tasks are assigned to the currently selected milestone; editing can move tasks to another milestone. Deleting a milestone with tasks is rejected until they are moved or deleted. Creator/admin manages task details and assignments; creator/admin can move any task between To do, In progress, and Completed (stored as `done`); any active assignee can update the shared status only for tasks assigned to them. Other active members may view the board. Task and milestone writes are allowed only while the project is Active. Paused and Completed projects are read-only for tasks and milestones; reactivating a Paused project restores editing, while Completed is final. Removing/leaving a member clears that member's assignments from unfinished tasks; completed task records remain. If a completed task is later reopened, assignments to inactive members are cleared before the status change. Assignment history is not a separate audit feature. Nonempty automatic milestones complete when all tasks are Done. Empty milestones remain incomplete until manually marked. Manual completion state persists until changed manually.

### `showcases` and `showcase_links`

- **Purpose:** Publish a public presentation for a completed project.
- **Showcase fields:** `id uuid`; `workspace_id uuid` unique; `title text`; `overview text`; `status text` (`draft`, `published`, `unpublished`); `published_at timestamptz` nullable; `updated_by uuid`; timestamps.
- **Link fields:** `id uuid`; `showcase_id uuid`; `label text`; `url text`; `sort_order integer`.
- **Rules:** Publish only when workspace status is Completed. Creator/workspace admins manage the showcase. Contributor names are derived automatically from the opportunity creator, accepted collaboration applicants, and all current or former workspace members, not entered as arbitrary text. Names use each contributor's current public profile display name. Completed task count is not a publication prerequisite.

### `notifications`

- **Purpose:** Persist in-app notifications.
- **Fields:** `id uuid`; `recipient_id uuid`; `actor_id uuid` nullable; `event_type text`; `entity_type text`; `entity_id uuid`; `created_at timestamptz`; `read_at timestamptz` nullable; `metadata jsonb` limited to non-sensitive presentation context.
- **Rules:** Generate notifications through trusted database functions for requests/decisions, workspace invitations/membership and role changes, task assignments, project status, likes, comments, and replies. Likes/comments never notify their own author; replies notify the parent comment author and opportunity owner without duplicate rows. For an immediate project invite, notify the invitee when active membership is created. Recipients can read their notifications and change only their own read state. Resolve destinations through current authorization and avoid exposing deleted/private content. Closing or deleting an opportunity silently removes pending requests and sends no cancellation notification.
- **Event types:** `request_received`, `request_decided`, `workspace_invite`, `member_joined`, `member_left`, `member_removed`, `member_role_changed`, `task_assigned`, `project_status_changed`, `opportunity_liked`, `comment_added`, and `comment_replied`.

### `storage_cleanup_jobs` (internal)

- **Purpose:** Preserve exact object paths for retryable Storage API deletion when a relational lifecycle transition cannot atomically remove object bytes.
- **Fields:** `id uuid`; `bucket_id text` constrained to configured application buckets; `object_path text`; `authorized_user_ids uuid[]` derived by a trusted operation; `created_at timestamptz`; `attempt_count integer` default 0; `last_attempt_at timestamptz` nullable.
- **Rules:** Each row is a pending job; enforce unique `(bucket_id, object_path)`. No browser table read or write. Trusted functions enqueue jobs before deleting/replacing parent metadata, return only jobs authorized for the caller, and remove the job after Storage API deletion succeeds or the object is confirmed absent. Storage DELETE policy checks a matching pending job and caller membership in its authorization list. The job has no FK to parent records so it survives hard deletion. Without a background worker, retries happen when an authorized user returns; time-bounded deletion is not guaranteed.

## 3. Relationships

| Entity A         | Relationship | Entity B                                | Rules                                                                                            |
| ---------------- | ------------ | --------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Auth user        | One-to-one   | Profile                                 | Profile keyed by Auth user ID; no public email copy.                                             |
| Profile          | Many-to-many | Skill                                   | Through `profile_skills`; skills are shared and case-insensitive.                                |
| Opportunity      | Many-to-many | Skill                                   | Through `opportunity_skills`.                                                                    |
| City             | One-to-many  | Profile / opportunity                   | Optional predefined city; `Other` text is stored separately.                                     |
| Opportunity      | One-to-many  | Like / comment / request                | Deleted opportunity removes public engagement; accepted requests preserve collaboration history. |
| Comment          | One-to-many  | Reply comments                          | Self-reference; every reply must use the same opportunity.                                       |
| Accepted request | Zero-or-one  | Private conversation                    | Conversation exists only for private-chat acceptance.                                            |
| Opportunity      | Zero-or-one  | Workspace                               | Unique `workspaces.opportunity_id`.                                                              |
| Workspace        | One-to-many  | Membership / message / milestone / task | Access depends on current active membership.                                                     |
| Task             | Many-to-many | Profile assignees                       | Through `task_assignees`; assignees update status only on assigned tasks, the owner/admins can update any. |
| Milestone        | One-to-many  | Task                                    | Every task belongs to exactly one milestone; milestone deletion is restricted while tasks remain linked.       |
| Workspace        | Zero-or-one  | Showcase                                | A workspace has one showcase record, which may be draft/unpublished/published.                   |
| User             | One-to-many  | Notification                            | A notification has one recipient and optional actor.                                             |

## 4. Integrity and business invariants

- **INV-01:** A profile has one Auth identity; username is unique with case-sensitive comparison.
- **INV-02:** Shared skills have a unique normalized case-insensitive name; concurrent additions resolve to the existing catalog entry.
- **INV-03:** Predefined city and free-text `Other` are mutually exclusive on each profile/opportunity.
- **INV-04:** An opportunity's `Other` project type requires a custom label; non-Other types do not carry one.
- **INV-05:** Experience selections contain one or more valid levels without duplicates. `any_level` is exclusive and cannot be combined with a specific level.
- **INV-06:** At most one request row exists per applicant/opportunity at a time. Only verified applicants can create one while the opportunity is open. Rejected/withdrawn rows prevent resubmission; closing deletes pending rows and permits a fresh request after reopening.
- **INV-07:** An accepted request has exactly one acceptance path. Private-chat path creates a private conversation; workspace path creates/uses the opportunity's sole workspace and membership.
- **INV-08:** Closing an opportunity prevents new requests and silently deletes pending request rows, while likes/comments remain available. Affected applicants may reapply after reopening. Deleting removes the public listing, likes, comments, and all non-accepted requests but retains accepted collaboration/workspace details privately for existing collaborators.
- **INV-09:** The opportunity creator remains the workspace owner for the MVP, has an active owner membership, and cannot leave or be removed. Ownership transfer is out of scope.
- **INV-10:** A workspace member without an active membership has no access to workspace chat messages, attachments, or Storage objects, including items created before removal.
- **INV-11:** Only the two participants of an active private conversation can access its messages/files. Ending removes access and deletes messages and file objects.
- **INV-12:** Task status is one of To do / In progress / Done (shown as Completed on the board); assignee membership is unique per task; each task has exactly one milestone. Creator/admin can change any task status; assignees can change status only on their assigned tasks.
- **INV-13:** Automatic milestone completion reflects all linked tasks being Done when at least one task exists. Empty milestones remain incomplete unless manually completed. Manual mode persists until a creator/admin changes it.
- **INV-14:** Project begins Active. Only the permanent project owner (the opportunity creator) can change status. Paused may return to Active; Completed is terminal. Task and milestone writes are allowed only while Active. Project deletion is a separate permanent owner-only operation and removes project data and its showcase.
- **INV-15:** A showcase can be published only for a Completed workspace. Contributors are the project creator, accepted collaboration applicants, and every current or former workspace member, derived from request and membership history.
- **INV-16:** Public reads expose profile and catalog data but do not expose the identities of users who liked an opportunity; public like counts are aggregated, and each user can read their own like state.
- **INV-17:** Database functions that perform multi-row transitions validate `auth.uid()`, verified email where required, ownership/membership, and current state; they commit atomically and are safe against duplicate submission.
- **INV-18:** A deleted comment has `body = null` and a non-null `deleted_at`; its row and parent relationship remain so replies can still be displayed.

| Data / query pattern               | Index or optimization                                                                                                     | Reason                                                                                                                 |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Case-sensitive username lookup     | Unique B-tree on `profiles.username`                                                                                      | Profile route and uniqueness.                                                                                          |
| Skill lookup and relationships     | Unique B-tree on `skills.normalized_name`; indexes on both join-table foreign keys                                        | Autocomplete, deduplication, directory and opportunity filtering.                                                      |
| City directory/opportunity filters | Index `city_id`; index active city names by `normalized_name`                                                             | Search and location filters.                                                                                           |
| Public opportunity feed            | Partial index on `(created_at desc)` for undeleted listings; index `status` as needed                                     | Feed ordering and open/closed state.                                                                                   |
| Opportunity keyword search         | PostgreSQL full-text GIN index over title and description for undeleted public opportunities                              | Keyword discovery.                                                                                                     |
| Opportunity skill filters          | Index `opportunity_skills.skill_id` and `(opportunity_id, skill_id)`                                                      | Filter and detail load.                                                                                                |
| User's likes and like counts       | Index `(user_id, created_at desc)` plus primary key `(opportunity_id, user_id)`                                           | Profile/account views and duplicate prevention.                                                                        |
| Comment threads                    | Index `(opportunity_id, created_at)` and `parent_comment_id`                                                              | Load top-level comments and nested replies.                                                                            |
| Request inbox/history              | Unique `(opportunity_id, applicant_id)` plus `(opportunity_id, status, created_at)` and `(applicant_id, created_at desc)` | Duplicate prevention, creator inbox, and applicant history; deleting pending rows on close permits retry after reopen. |
| Chat timeline                      | `(conversation_id, created_at)` / `(workspace_id, created_at)`                                                            | Chronological history and catch-up after reconnect.                                                                    |
| Current workspace membership       | Partial unique index on `(workspace_id, user_id)` where `ended_at is null`; lookup index on `(user_id, workspace_id)`     | Immediate access/revocation and role checks.                                                                           |
| Tasks and milestones               | `(workspace_id, status)`; `(milestone_id)`; task-assignee index `(user_id, task_id)`                                      | Workspace board, milestone progress, and assignee views.                                                               |
| Notifications                      | `(recipient_id, created_at desc)` and partial unread index where `read_at is null`                                        | Notification feed and unread count.                                                                                    |

## 6. Access and data lifecycle

- **Public reads:** All profiles, all skill catalog entries, active cities, undeleted opportunities, comments for undeleted opportunities, aggregated like counts, and published showcases are public. Profiles and skills have no active/inactive state in this schema. Public reads never expose liker identities, email, private request messages, workspace membership, chat, or notification data.
- **Profile writes:** A user reads/updates their own profile, skills, and links. Public profile fields may be read by anyone. Username uniqueness is case-sensitive. Optional profile completion never gates participation.
- **Opportunity writes:** Public read while not deleted; creator manages own record. Verified-email requirement for publish and request is checked in trusted functions/policies. Signed-in users may like/comment on open or closed undeleted listings; email verification is not required.
- **Requests:** Applicant reads their own request; opportunity creator reads requests for their opportunity. Mutations are limited by role and status. Closing silently deletes pending request rows; the applicant may submit again if the opportunity reopens. Rejected/withdrawn rows remain terminal. Cancellation sends no notification.
- **Deleted opportunity:** If accepted collaboration or a workspace exists, retain the soft-deleted opportunity and accepted context for authorized participants while removing its public listing, likes/comments, and all non-accepted requests. Otherwise, hard-delete it and dependent records. Never treat `deleted_at` as public access.
- **Private chat:** Only the two active participants read/write. Ending collaboration revokes access and deletes messages and file objects. Keep only the minimal accepted-request/conversation tombstone needed to enforce no reapplication and history rules.
- **Project:** Only current active members read project data. The permanent creator/owner appoints admins; owner/admins manage invitations, membership, tasks, milestones, and showcase; creator/admin can change any task status and an assignee can change status only on tasks assigned to them, while the project is Active. Removing or leaving ends access to all project chat history and files immediately. Preserve membership and chat history records for remaining members; retain ended membership rows for contributor attribution.
- **Storage:** Use private buckets `profile-media`, `private-attachments`, and `workspace-attachments`, each capped at 10 MiB. Profile images accept only JPEG, PNG, GIF, or WebP. Chat attachments use the extension/MIME allowlist above. Profile media is accessible only while referenced by a profile; private chat and project objects require active participant/member access. Object paths start with their parent UUID; attachment paths also include the uploader UUID. Upload unique paths without overwrite. Configure buckets through the Supabase Dashboard/Storage API; migrations must not write to Storage system tables. Object deletion uses the Storage API, not direct SQL against `storage.objects`.
- **Cleanup jobs:** `storage_cleanup_jobs` is an internal operational table containing exact bucket/path, authorized user IDs derived by a trusted function, and retry timestamps. No browser table access. Trusted functions enqueue paths before relational references are removed; authorized clients delete via Storage API and acknowledge completed jobs through a function. Ended private-chat objects are unreadable immediately and eligible only for queued deletion. Without an Edge Function/background worker, retries happen when an authorized user returns; time-bounded deletion is not guaranteed.
- **Audit history:** No general audit-log product feature is required. Preserve business records needed for accepted collaboration and workspace history. Do not log secrets or chat/file contents.
- **Retention:** Workspace chat content remains for current workspace members after a member is removed, but is inaccessible to the removed user. Private chat content is deleted when either participant ends collaboration.

## 7. Migrations and reference data

- **Migration approach:** Versioned SQL migrations in `supabase/migrations/`; T-01 defines core entities, constraints, indexes, invariant triggers, default-deny RLS, trusted workflows, and Storage object policies/cleanup functions. The historical migration chain still checks four buckets. For a clean project, create `profile-media`, `private-attachments`, `workspace-attachments`, and the legacy `opportunity-media` bucket to apply that chain, then apply the cover-image cleanup migration and remove the unused bucket through the Supabase Dashboard after its objects are removed. T-03 applies the complete chain reproducibly to a clean development project before production review.
- **Reference data:** The core migration inserts the predefined city catalog with stable IDs and `ON CONFLICT DO NOTHING`. No fictional profile/opportunity fixtures or reset jobs are planned. Reviewers can create records through the product; those changes persist.
- **Compatibility / rollback:** Prefer additive migrations and explicit backfills. Avoid destructive schema changes that lose user or workspace history. Reversals that would discard production data require a recovery plan and manual review.

## 9. Remaining schema and implementation notes

- **Account deletion:** Self-service account deletion and associated cleanup/anonymization are out of scope for the MVP.
- **Settled MVP choices:** The `cities` seed order and `any_level` exclusivity are specified above. Chat attachments use the explicit extension/MIME allowlist and 10 MB per-file cap. Deleted comments retain a body-free placeholder row so nested replies remain connected. Pending requests deleted on close permit retry after reopening; rejection/withdrawal do not. Showcase contributors include accepted applicants and all workspace members, past and present.
- **Implementation follow-through:** Migrations must preserve accepted collaborations on opportunity deletion, retain ended membership rows for showcase attribution, and add the private `storage_cleanup_jobs` operation described above. Task assignment history beyond current assignees is not an MVP audit feature.
